# 仕様を書く

リポジトリルートの `AGENTS.md`、`docs/development-workflow.md`、`docs/project-context.md` を適用する。
入力は対象 Issue または機能要望。Issue がなければ草案として扱い、存在しない番号や決定を作らない。

1. 要望と既存コード・テスト・関連資料を調べ、現在の振る舞いと制約を把握する。新規プロジェクトでは既存実装がないことを明記する。
2. 背景、利用者、目標、対象外を区別する。確認済みの事実と仮定を明示する。
3. 正常系に加え、空入力、エラー、権限、互換性など関係する境界条件を整理する。無関係な観点を増やさない。
4. 観察可能な受け入れ条件に落とし込み、各条件の確認方法を対応付ける。
5. 影響する領域、実装手順、test / lint / typecheck / build の方針をまとめる。実装を求められていなければコードを変更しない。
6. 実装を止める未決事項と、仮定して進められる事項を分ける。重要な選択には選択肢と影響を添える。

出力は Issue に貼れる仕様草案。大きい仕様をファイル化する場合は、合意した保存先（例: `docs/specs/123-feature.md`）に保存して Issue から参照する。
構成は「背景 / 目標・対象外 / 要件 / 境界条件 / 受け入れ条件と確認方法 / Plan / 未決事項」。
GitHubへの投稿は依頼・既存の許可がある場合に限る。
