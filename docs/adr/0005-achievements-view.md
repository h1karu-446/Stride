# ADR-0005: 達成の記録は、ビューで4種類をまとめて作る

| 項目 | 内容 |
| --- | --- |
| ステータス | 承認済み |
| 日付 | 2026-09-29 |
| 関連 | [機能仕様書 BR-09](../specs/study-plans.md) / [技術設計書 4.5](../design/study-plans.md) |

## 状況

Journeyの達成の記録には、やりたいことの達成、計画の完了、マイルストーン、教材の完了の4種類を、月ごとの時系列で並べる（FR-18）。どれも状態を戻すことができ、戻したら記録から消える必要がある。

4種類のデータを、どうやって1つの時系列にまとめるかを決める必要があった。

## 決定

4つのテーブルを `union all` するビュー `achievements` を作り、`security_invoker = true` で元のテーブルのRLSを効かせる。画面は月の範囲を指定して、日付の新しい順に取得する。

## 検討した案

| 案 | 概要 | 評価 |
| --- | --- | --- |
| A. ビュー（採用） | 元のデータから毎回組み立てる | 元のデータと記録が食い違わない。状態を戻せば自動で消える。書き込み処理が増えない |
| B. 達成イベントのテーブル | 完了・達成のたびに、トリガーや画面から記録用のテーブルに書き込む | 状態を戻したときに記録の削除も必要になり、二重管理になる。書き込み漏れの危険がある |
| C. 画面で4つを取得して結合 | 4回取得し、画面で並べ替えて月ごとにまとめる | 月単位の取得（もっと見る）を4種類それぞれで行う必要があり、処理が複雑になる |

## 影響

- 良くなること
  - 記録のためだけの書き込みやトリガーが要らない
  - 並び替えと期間の絞り込みを1回の取得で行える
- 引き受けるデメリット
  - 「一度達成して、後で戻した」という履歴は残らない。今の仕様（戻したら消える）には合っている
  - 載せる種類や列を変えるときは、ビューを作り直す migration が必要
