# ADR-0003: 削除したルーティンタスクは、削除トリガーでスキップを記録する

| 項目 | 内容 |
| --- | --- |
| ステータス | 承認済み |
| 日付 | 2026-09-29 |
| 関連 | [機能仕様書 BR-02](../specs/study-plans.md) / [技術設計書 4.4・6.3](../design/study-plans.md) / [ADR-0002](0002-generate-routine-tasks-on-open.md) |

## 状況

ルーティンタスクはTodayを開くたびに生成を試みる（ADR-0002）。ユーザーがTodayでルーティンタスクを削除しても、次に開いたときにまた作られてしまう。「その日は削除した」ことを覚えておく仕組みが必要だった。

## 決定

`tasks` の AFTER DELETE トリガーで、削除した行に `routine_id` があれば `routine_skips (routine_id, date)` を記録する。`generate_routine_tasks` はスキップ記録がある組み合わせを除外する。

## 検討した案

| 案 | 概要 | 評価 |
| --- | --- | --- |
| A. 削除トリガーで記録（採用） | 既存の削除操作をそのまま使い、DBが自動で記録する | 画面の変更が要らない。記録漏れが起きない |
| B. 論理削除 | `tasks.deleted_at` を追加し、削除の代わりにフラグを立てる | タスクを読むすべての処理とスコア計算（`calculate_daily_score`）に除外条件が必要になる。スコア計算を変えない方針（NFR-02）に反する |
| C. 画面で削除と記録を両方送る | 削除時に `routine_skips` への insert も送る | 2回の書き込みの片方だけ失敗すると記録が漏れる。削除する場所が増えるたびに同じ処理が必要 |

## 影響

- 良くなること
  - Todayの削除処理は既存のまま変えなくてよい
  - スコア計算やタスクの読み込みに影響しない
- 引き受けるデメリット
  - コードから見えない副作用（削除すると別テーブルに行が増える）ができる。migration のコメントと `docs/project-context.md` に明記する
  - 計画の削除（`delete_plan`）で未来のルーティンタスクを消したときもスキップが記録されるが、直後の計画の削除で cascade して消えるので問題はない
