# 開発ワークフロー

## 1. Issue を定義する

機能追加・バグ・作業用テンプレートから Issue を作成する。背景、受け入れ条件、対象外、担当を明確にする。
原則1つの Issue を1つの PR で完結させる。大きい場合は親 Issue と独立して検証可能な子 Issue に分ける。
複数 Issue を1 PRへまとめる、または1 Issue を複数 PRへ分ける場合は、理由・依存関係・完了条件を記録する。

初回テンプレート導入は Issue 作成前に行ってよい。初回セットアップでは [導入・管理ガイド](ai-dev-starter-guide.md) に従い、Contextを設定し、ルートREADMEをアプリの説明へ書き換える。既存アプリではREADMEを保持し、開発文書へのリンクを追加する。ガイドは導入先に残す。初回セットアップ後、最初の Issue に導入内容と未決事項を記録する。
GitHub が使えない場合はローカルに Issue 相当の草案を作って進め、復旧・投稿許可後に転記する。

## Workflow mode（Issueごと）

プロジェクト既定値は `standard`。人間がIssueのWorkflow Mode欄で1つ選択し、Issue指定を優先する。
未指定・両方選択は `standard` として扱う。Agentは勝手に `standard` から `light` へ落とさない。
小変更では `light` を提案してよいが、人間が選択するまでは `standard` を維持する。
`light` の範囲を超えたら `standard` の手順を適用し、Issueに理由を記録する。

必須・省略可能手順はこの表でのみ定義する。以下の各節は具体的な実施方法を説明する。

| 手順 / 対象 | light | standard |
| --- | --- | --- |
| 対象 | typo、docs、小規模で低リスクな変更 | feature、bug、dependency、DB/API、production logic等 |
| Issue・受け入れ条件 | 必須 | 必須 |
| Plan | 数行で必須。詳細仕様書は省略可 | 変更範囲・リスク・検証方法を記録 |
| 検証 | 変更対象の確認は必須。無関係なtest / lint / typecheck / buildは理由を記録して省略可 | Contextの4項目を評価。対象なしは理由付きN/A、実行不能はBLOCKED |
| 別Agentレビュー | 省略可。省略理由を記録 | 必須。利用不能時は第5節の例外手順 |
| Human review | 必須 | 必須 |
| PR・検証結果・指摘対応・引き継ぎ | 必須（該当なしは理由を記録） | 必須（該当なしは理由を記録） |

## 2. Plan first

Issue、関連コード、テスト、Context を確認し、実装前に次を Issue 本文またはコメントに記録する。
投稿できない場合はチャットまたはローカル文書に残す。

```markdown
## Plan
- 目的 / 受け入れ条件:
- 変更する領域:
- 実装手順:
- 検証方法（test / lint / typecheck / build と受け入れ条件の確認）:
- 対象外 / リスク / 未決事項:
```

仕様整理が必要なら `spec-writing`、不具合の原因が不明なら `bug-investigation` を使う。
通常の判断は既存の許可範囲で進める。破壊的な変更や仕様上の重要な選択が未確定なら、判断材料を整理して確認する。
実装中に前提が変わった場合は計画を更新する。小さな文言修正にも短い計画を残すが、長い仕様書は不要。

## 3. 実装する

- 最新の基準ブランチから作業ブランチを作る。例: `feat/123-profile`, `fix/124-login`。
- 既存の未コミット変更と進行中の作業を確認する。担当者同士で同じ作業ブランチを同時編集しない。
- Issue の範囲で変更し、バグ修正では再発を検出できるテストを可能な限り追加する。
- 振る舞い・設定・運用が変わる場合は関連ドキュメントも更新する。

## 4. 検証する

選択したmodeの表に従い、Context に定義した4項目の適用範囲を評価する。テンプレート整合性CIはアプリの検証を代替しない。

| 項目 | 記録する証拠 |
| --- | --- |
| test | コマンド、対象、結果。必要に応じて回帰・受け入れテスト |
| lint | コマンド、結果 |
| typecheck | コマンド、結果。型検査を採用しない場合は理由 |
| build | コマンド、結果。ビルド対象がない場合は理由 |

結果は PASS / FAIL / BLOCKED / N/A。環境不足や未設定のコマンドは BLOCKED、対象そのものが存在しないと確認できた場合、またはmodeの表で省略可能な無関係の検証は理由付き N/A。
失敗を既存問題として除外する場合は比較結果と別 Issue を示す。UIの変更は操作・表示も、データ変更は移行・復旧も必要に応じて確認する。

## 5. PR と別Agentレビュー

PR テンプレートを埋め、原則 `Closes #番号` で対象 Issue を結ぶ。未完了の分割 PR は `Refs #番号` とする。
PR の作成・投稿は許可された範囲で行い、未許可なら本文を草案として渡す。

別Agentレビューを実施する場合は、実装者とは別の Agent / セッションに `pr-review` を依頼する。別モデルは必須ではないが、実装者の自己レビューだけで代用しない。
共通のsource of truthは `skills/pr-review/SKILL.md`。Claude Codeでは `reviewer` subagentを明示して依頼する。
`.claude/agents/reviewer.md` はClaude固有の薄いラッパーであり、Codexが自動で読む設定ではない。
Codexでは別Agentを起動し、`skills/pr-review/SKILL.md` を読んでレビューするよう依頼する。
別Agent起動がない環境では別セッションへ同じ依頼を渡す。skillを実装セッションで呼ぶだけでは独立レビューにならない。
依頼には Issue、受け入れ条件、base / head commit、差分、検証結果を渡す。結論を誘導せず、レビュー担当は読み取り中心で独立して検証する。
別Agentの起動や外部サービス利用は、その環境の権限とユーザーの許可範囲で行う。

```text
Issue #123 と PR #45 を pr-review の手順で独立レビューしてください。
対象: base=<SHA>, head=<SHA>
受け入れ条件と差分を確認し、根拠付きの指摘、確認済み範囲、未確認事項を報告してください。
コードの修正・マージは行わないでください。
```

- P0: 即時対応が必要な重大障害・損失。P1: マージ前に修正すべき重大な不具合。
- P2: 具体的な条件で生じる不具合・受け入れ条件の欠落。修正するか担当者が理由付きで延期を判断する。
- P3: 軽微な改善。好みだけの指摘を必須修正にしない。
- 指摘ごとに対応 / 見送り理由を記録する。修正後は影響する検証を再実行し、レビュー対象の変更部分を再確認する。
- レビューには担当 Agent、日時、対象 head SHA、指摘、対応を残す。古い SHA へのレビューを新しい変更の確認済み証拠にしない。
- 別Agentを利用できない場合は「別Agentレビュー未実施」と明記する。人間がレビューして例外を承認するか、レビュー待ちを残す。黙って自己レビューへ置き換えない。

## 6. 引き継ぎ・マージ

担当が変わるときは次を Issue / PR に記録する。

```markdown
## Handoff
- Issue / PR / branch / head SHA:
- 完了したこと:
- 決定と理由:
- 検証結果とレビュー状態:
- 残作業 / blockers:
- 次の一手:
```

マージ可能の条件は、受け入れ条件の達成、必要な検証の成功、N/Aの説明、重大指摘の解消、選択modeのレビュー要件の充足、Human reviewの記録、ドキュメント更新。
FAIL / BLOCKED が残る場合は完了としない。マージ・デプロイは担当者の権限と既存の許可に従い、この文書だけを許可とみなさない。

GitHub の必須チェック・承認ルールは別途設定する。AIレビューコメントが GitHub の人間による承認要件を満たすとは限らない。

## 7. Worktree Management

- Issue / PR単位の作業では、必要に応じてGit worktreeを使用する。
- worktreeは一時的な作業環境として扱う。
- main worktreeは削除しない。
- 作業完了後は、以下を確認する。
  - 未コミット変更がない
  - 必要な変更がpush済み
  - PRがmerge済み、またはworktreeが不要と判断できる
- 上記を満たす場合のみworktreeを削除してよい。
- 未merge・未commitの変更があるworktreeは削除しない。
- 削除前に対象branch / worktreeを確認する。
- 作業完了時に以下を報告する。
  - 使用branch
  - 使用worktree
  - PR状態
  - cleanup可能か
